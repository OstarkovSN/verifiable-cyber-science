# Human-in-the-loop scientific protocol

This protocol describes a scientist agent working with a human researcher. It is provider-agnostic; the current implementation launches only native Codex. No scientific balls run or completed-science result is claimed here. See README.md for the executable interface and its limits.

1. The human supplies a scientific question in natural language, together with observations and any available background information. The current question is `protocols/v1/task-balls.txt`; the versioned scientist instructions are `protocols/v1/instructions.txt`. Neither supplies a worked solution, expected answer, preset prior family or parameters.
2. The agent proposes a mathematical model. It distinguishes supplied facts from modeling choices, extra assumptions and external evidence. If the information does not determine a unique answer, it explains the ambiguity and gives a conditional conclusion with the assumptions visible. The human evaluates whether those choices describe the intended scientific question.
3. The agent may use tools, including Internet research, calculations and Lean. When useful, it requests additional literature, calculations, experiments or human clarification through the request tool. Such requests are optional. A request stops execution until a real response is supplied with its provenance; the agent incorporates that response and records its limitations. It must never fabricate a response or treat external evidence as guaranteed true.
4. The agent writes a substantive formalization and proof of its model, observation, Bayesian update and prediction. It runs the actual Lean checker, reads the real diagnostic output, and revises the proof and, when necessary, the model and conclusions. Arithmetic for a value obtained elsewhere does not establish the scientific inference. The implementation automatically returns host-check failures or incomplete candidates for revision, with a bound of three cycles per invocation. Client, authentication or quota failures stop execution. Hitting the bound requires explicit resume.
5. After submission, the host freezes the candidate and independently checks it in a container without network or authentication. Lean compiles the proof, a separate leanchecker process rechecks the kernel, and a kernel-environment audit lists additional axioms and proof gaps. The extractor follows the exact conclusions through local definitions and assumptions, writes a standalone Lean file, recompiles it and compares the extracted statements with those actually proved. Imported pinned libraries are the trusted base. Failed, missing or timed-out checks do not establish a result.
6. The human receives the actual model, assumptions, external sources, proof scope and exact conclusions. For each frozen attempt these are in `control/attempt-NNN/candidate.json`, `report.txt`, `Model.lean`, `packet.json`, `verification/extracted.lean`, `verification/extracted.json`, `verification/lean.log` and `checker-trace.log`. The packet includes verification and runtime provenance. The human judges scientific relevance, the distinction between facts and choices, sampling and modeling assumptions, source use, gaps and the exact conclusion. Successful Lean checking alone cannot make this judgment. Any additional axiom or sorry produces a conditional `proved_if` result, including unused additions; human acceptance preserves that condition.
7. The human explicitly accepts or rejects a frozen, content-bound attempt and records a reason. Rejection is feedback to revise the model, assumptions, conclusions and proof; explicit resume starts a fresh context with that feedback and the run history. An unchanged rejected candidate is refused. Acceptance records the human decision for the exact frozen artifacts, not subsequent working drafts. Changing an artifact invalidates the review binding. The agent cannot approve itself.
8. The run retains raw scientist traces, submitted proofs and narratives, manifests, extraction and checking evidence, external responses with provenance, revision lineage, and human decisions. Failed checks and retry feedback remain inspectable. Requests and reviews never launch inference themselves. Versioned task and instructions are copied to host custody and hashed; changing them requires a new run.

The scientist starts from the natural question, current instructions, installed libraries and its own run history. Its filesystem excludes previous answers, task-specific proofs, preset prior families, historical artifacts and other runs. It must not search for those prior solutions. Internet access is available for current research and the subscription client, so this is a filesystem boundary, not a destination firewall. Only the normal native subscription authentication file is mounted as an explicit exception; it is never scientific evidence and must not be read, copied or logged by the scientist. API-key fallback, paid services and additional agents are forbidden. Authentication and quota errors stop the workflow.

The current Lean interface is one proof file with explicit pinned Mathlib imports, a 24,000-byte proof-body limit, top-level conclusion declarations with binders after the colon, and no executable metaprogramming or custom syntax. Native Mathlib tactics remain available. The implementation reports unsupported syntax as errors. If these limits prevent a meaningful formalization, the agent must explain that limitation rather than claim an unrelated smaller result answers the question.
