SUPPLEMENTARY INFORMATION — WORKING DRAFT
Machine-verified LLM-driven science and what humans still need to decide

S1. Scope and experimental design

We used four scientific reasoning scenarios: Bayesian prediction for balls drawn from a box, inference of fish species and population sizes in a lake, the timing of salt addition when heating water, and coffee cooling. Each question was supplied in natural language to a terminal agent. The agent proposed a mathematical model, identified additional assumptions, and attempted to derive an answer in Lean. A human researcher reviewed the assumptions, definitions and conclusions of machine-checked submissions and could require further revisions.

The questions were investigated separately with Codex and Claude Code. These were demonstrations of the workflow, with iterative human feedback. They were not a controlled comparison of model performance. The provider's native client, its built-in instructions and tools, the selected model, and the subsequent human feedback could differ between runs. No physical measurement device was connected. The lake observations supplied during these runs were generated by a simulator; chosen cup, heater and material parameters were scenario assumptions unless accompanied by external evidence.

This draft describes the recorded protocol and inputs. The accompanying run-inventory.json is a dated preparation snapshot. Final scientific results, revision counts and the selection of examples for the paper remain to be completed after human review.

S2. Software and execution environment

The harness is available in the private repository https://github.com/OstarkovSN/verifiable-cyber-science on branch feat/three-task-runs. The code inspected for this draft was commit 0ae2ac3a74be3c6611445094582466dfe705c507. Earlier runs used earlier revisions; the checking-source hashes recorded with each submission identify the code used for that submission. This reference commit should not be assigned retrospectively to every run.

The harness is a Python command-line application using Click, with dependencies locked by uv. Its declared Python requirement is version 3.11 or newer. The recorded clients were Codex CLI 0.166.0 and Claude Code 2.1.325. The requested models were gpt-6.1-sol and claude-sonnet-5-5, respectively, with medium reasoning effort. These are the model identifiers requested through the native clients, rather than a claim to have recorded the providers' underlying model weights or every server-side setting. Each run records the selected executable's version and hash. The provider-supplied system instructions were not authored or equalized by us.

Formal checking used Lean 4.35.0 and a pinned Mathlib dependency set. The recorded library manifest has SHA-256 9e10a38d592324e664c1cb74b7fe00473782bff3940506d50f8e59059549f328. The Docker image used locally had image ID sha256:c0e8df9380519cf514d5fbb5aeaa7aa5de5f32c50330badcadc05cdabaae5566 and was identified as python:3.13-slim when tested. A local image ID does not provide a portable registry reference; a distributable image specification remains an item for the reproducibility release.

Each invocation started a fresh Docker container with a temporary home directory and client configuration. The agent could write to its own run workspace and temporary directories. Selected harness files, the current task and instructions, the native executable and the Lean installation and library builds were mounted read-only. Other runs, previous solutions, the host's home directory, global CLAUDE.md and client configuration, repository history and the Docker socket were excluded. Internet access was available for the native client and literature research. The filesystem isolation did not restrict the network to a fixed list of destinations.

The existing native subscription credential file was mounted read-only as an exception required for authentication. It was excluded from scientific evidence and export. The harness checked the subscription authentication type; authentication and quota failures stopped the run rather than switching to an API key or paid fallback.

The paired salt and coffee runs used limits of 4 GiB memory and two CPUs per scientist/checker job. The later lake-inventory runs used 3 GiB and two CPUs. Resource fields absent from older run records are left unspecified in the inventory. The matrix launcher allowed at most three concurrent jobs. A scientist invocation had a two-hour timeout; independent checking had a 3,000-second timeout. Failed or incomplete host checks could trigger up to three cycles within one start or resume invocation. Client failures required intervention. Claude Code also had an 80-turn limit. These execution limits could affect completion and are part of the procedure.

S3. Agent instructions and revision cycle

The supplied task did not specify a worked solution, a prior family, fitted parameters or an expected answer. Instructions required the agent to distinguish supplied facts from its own modeling choices, prefer deriving parameters from observations over choosing convenient values, and connect the scientific inference to the final Lean theorem. They also required readable assumptions and conclusions, with derivable algebra, normalization and parameter calculations moved into intermediate lemmas where possible.

The exact task and instruction files are supplied in the inputs directory. The two balls tasks were byte-identical. Their instructions differed in one authentication sentence: the Codex version named the native Codex client, while the Claude version referred to the native subscription client. The Claude balls launch also included an initial human clarification requesting a usable predictive model rather than a nonidentifiability counterexample; this text is included separately. Salt, coffee and lake-inventory runs used the common v2 instructions, with identical task and instruction bytes within each pair. Later feedback and external responses belong to the individual run record.

The launcher constructed each prompt from the instruction text, task, cycle number, a reminder to inspect the run's own history and checker feedback, and any recorded initial clarification, human decisions and external responses. A resume used a fresh native client context while retaining the workspace and recorded history. The complete prompt therefore changed after requests or reviews; the instruction file alone is not the full conversation.

The agent could run shell commands, inspect and edit its workspace, consult the Internet, and invoke the harness's check and request tools. Requests were classified as literature, calculation, experiment or clarification. A request stopped the cycle. An operator then supplied a response with provenance and explicitly resumed the run. A response did not itself launch inference. Synthetic observations and calculations were identified as such. The scientists did not receive one another's proofs, models or answers.

After a rejected submission, the next cycle received the recorded human decision and feedback. The agent could revise the model, assumptions, conclusion and proof. An unchanged rejected candidate was refused. These feedback-driven revisions were part of the human-in-the-loop procedure, rather than independent repetitions of the initial experiment.

S4. Formal checking and extraction

The agent submitted a Lean file, a plain-language report and a candidate manifest naming the final conclusion theorem or theorems. The host copied these into a frozen attempt directory. It then checked the submission in a separate container without network access or subscription credentials. The process compiled the proof with Lean, audited axioms and proof gaps, and ran a separate leanchecker process to recheck the proof.

The extractor followed the named conclusions through local declarations and emitted a standalone Lean file containing the statements and definitions needed for review. It recompiled this extraction and compared the complete kernel expressions and the reached declarations' types and values with the original checked environment. The exact dependency set was therefore checked algorithmically. Scientific interpretation of these declarations remained a human task. Imported pinned libraries formed part of the trusted base.

The interface accepted one Lean file with explicit Mathlib imports and a proof body of at most 24,000 UTF-8 bytes. It allowed definitions, structures, lemmas and theorem declarations, while restricting executable metaprogramming, custom syntax, namespaces, native_decide, IO and unsafe code. Ordinary supported Mathlib tactics remained available. Unsupported constructs produced explicit errors.

A successful ordinary check was reported as proved. Additional axioms or sorry introduced a conditional verdict, proved_if, including when an added declaration was unused. Compilation errors, missing reports, interrupted checks and timeouts were not proof acceptance. A valid proof established the checked conclusion from its formal premises and definitions; it did not establish that those premises described the intended physical system.

S5. Human review and evidence preservation

The researcher inspected the scientific assumptions, definitions needed to interpret the result, and exact conclusions, alongside the report and external sources. Review considered whether the assumptions were reasonable, whether the conclusion answered the question, and whether claimed derivations had instead been inserted as assumptions or definitions. A formal pass was a checkpoint for this review. Only an explicit human decision accepted a scientific submission.

Each decision referred to the hash binding of a frozen attempt. The binding covered the proof, report, manifest, extraction and checking artifacts; the decision receipt had a separate hash. Altering the artifacts invalidated the recorded acceptance. Rejection feedback, failed checks and prior submissions were retained. Raw native-client event traces, external responses, checker logs and revision lineage were kept in host-managed control directories outside the agent's writable workspace. The exported inventory lists the frozen attempt bindings and decision-receipt hashes without exporting credentials or host account information.

One infrastructure interruption required recovery of a lake scientist's output after a Docker restart disconnected the attached controller while the container continued running. The original trace was preserved. Recovery collected the continuing container's logs and its actual exit status, checked that the original 641 JSON events were an exact prefix of the recovered 859 events, and then used the normal submission-checking path. This recovery is documented in the local existing-container-recovery.json receipt; it was not a second scientific run or a human acceptance.

S6. Task formulations and external evidence

Balls in a box

I have a box that initially contained 50 balls, each either black or white. I drew 10 balls, all of which were black, and did not return them to the box. There are now 40 balls remaining. Other boxes of the same kind also initially contain 50 black and white balls. Across these boxes, the fraction of black balls has a mean of 0.75 and a standard deviation of 0.1. I do not know the original number of black balls in my particular box. Using Bayesian statistics, what is the probability that the next ball drawn from the remaining balls will be black?

Lake inventory

We are standing near an unnamed lake in North Karelia, eastern Finland. Your goal is to determine which fish species are present, propose a probability distribution for the number of individuals of each species, and derive the probability distribution of the total fish population.

No surveys, measurements or catches have been performed. You may propose observations or experiments and request their results. Fish must not be caught or removed from the lake.

The operator later supplied observations from a fixed fictional lake using a separate survey simulator. Both scientists received identical exported observation bytes. The simulator included habitat information, eDNA samples, camera and sonar observations, and calibration records. The species reference panel was not a list of species known to be present. Detection, false positives and transfer from calibration conditions required modeling choices. The simulator source and hidden census were withheld from both scientists. Its source revision was 9fbdfc20b38e02972069f898968b703c3e3e6572; the observation-file SHA-256 was 2b91b221e0145c57f1b2f0462166173ea82e222f9735f9e17808ffd52f9ace80. These exports were simulated data, not field measurements of a real Finnish lake.

Water boiling and salt

I want to boil saline water. I have poured 1 litre of water at 20 degrees Celsius into a pot and started heating it on a stove. I will add salt, and want the final salted water to reach its boiling point as quickly as possible. The salt quantity, pot, heater and room conditions have not otherwise been specified. At what water temperature, or after how much heating time, should I add the salt to make the salted water boil sooner?

Coffee cooling

I have a cup of coffee initially at 90 degrees Celsius and want to know when it will cool to 60 degrees Celsius. Choose a reasonable cup shape and size yourself, explicitly identifying these as chosen scenario details rather than measured facts. You may request measurements of temperature, cup geometry or surrounding conditions. No time-temperature measurements or cooling coefficients have yet been supplied. How long will the coffee take to cool to 60 degrees Celsius?

Salt and coffee runs could consult or request literature on material properties and heat-transfer models. Supplied literature was external evidence subject to source checking and model interpretation. No fitted cooling curve for the requested cup or physical heating experiment was supplied. The final SI will link each incorporated response to its source receipt and the submission using it.

S7. Reproduction and completion of this supplement

The repository's README.md and PROTOCOL.md document installation, start, request response, review and resume commands. Reproduction requires the recorded native client versions and existing subscription authentication, Docker, Lean and the pinned library builds. With these prerequisites, uv run vcs-protocol start launches a single task; --task-file and --instructions-file select its input files. Status, respond and review commands do not launch a scientist. Resume is explicit. Re-running a hosted model may produce a different proof or modeling choice; the archived frozen proof and extraction provide the evidence for the particular result reviewed here.

The accompanying inventory records each selected run's status at export time, exact input hashes, client settings, frozen attempt bindings and human decision receipts. Inputs and initial clarifications are included as text files. Runtime provenance is restricted to an explicit list of scientific and software fields; credential paths and account metadata are not exported. Archived attempts can be checked against their bindings without launching a model.

Before submission, complete the results tables from the final accepted attempts, select and package the supporting Lean files, checker logs, external-source receipts and human decisions, and verify the resulting archive. Add a portable container image specification, confirm the intended source-code access and release revision, and complete the final data-and-code availability statement. Runtime and token totals should be included only if consistently recoverable from the retained records. Claims of improved researcher efficiency would require a separate measurement; the present records establish the workflow and its reviewed examples.
